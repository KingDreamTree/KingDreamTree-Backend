# F12 — 운동 후 코치 대화 (피드백 루프) 설계

> **작성**: B파트 · 2026-08-14 · PM 공유용
> 기획 의도: *운동을 끝낸 날, 사용자가 코치와 자연스럽게 대화하고 →
> 대화 끝에 바뀐 루틴과 그 이유를 받는다.*

---

## 1. 전체 서비스 플로우 — 이 대화가 어디에 앉는가

```
① 사진 2장 (레퍼런스 · 사용자)
      ↓  포즈 판정 → 세그멘테이션 → 부위별 비교
② 체형 진단   "하체는 목표에 가깝고, 차이는 팔에서 가장 큽니다" + 목표 근접도
      ↓  (+ 인바디 있으면 수치 근거 강화)
③ 4주기 루틴   주 N일 × 4주기. 진단된 약점 부위에 볼륨 가중
      ↓
④ 운동 수행    오늘의 Day 완료
      ↓
⑤ ★ 코치 대화  "오늘 어떠셨어요?" → 자연스러운 대화 → 제안 → 합의
      ↓
⑥ 루틴 반영    대화 끝에 "이렇게 바꿨어요 + 이유" 카드 → 다음 운동부터 적용
      ↓
   (④~⑥ 반복) → 4주기 종료 → 재촬영 → ②로 (전체 루프 완성)
```

⑤·⑥이 이 문서의 범위다. **운동한 날마다** 돌고, 반영은 **다음 운동부터**다.

---

## 2. 핵심 설계 — "말은 자유롭게, 손은 묶는다"

사용자가 보는 것은 자유로운 대화다. 그러나 시스템 안에서 코치가 실제로
**할 수 있는 행동은 딱 4가지**로 묶여 있다.

| 코치의 행동 (Function) | 뜻 | 안전장치 |
|---|---|---|
| `adjust_intensity` | 세트·횟수·휴식 조정 | 상한 3중 검증 (슬롯·근육군·주간총량) |
| `replace_exercise` | 운동 교체 | **후보 목록 안에서만** — 없는 운동을 지어낼 수 없음 |
| `flag_contraindication` | 통증 부위 금기 등록 | 세션에 누적, 이후 모든 루틴에 반영 |
| `finalize_revision` | 대화 마무리 — 변경 요약 + 이유 확정 | 이걸 불러야만 루틴이 실제로 바뀜 |

왜 이렇게 하는가 — **이 서비스의 일관 원칙이다.**

> 진단 점수: 판정은 VLM, 산수는 코드
> 루틴 생성: 선택은 LLM, 골격·상한은 코드
> **코치 대화: 말은 LLM, 변경은 코드가 검증한 도구 4개로만**

"AI랑 대화하다가 루틴이 이상해졌어요"가 구조적으로 불가능하다.
대화가 어디로 흘러도, 최종 변경은 후보 집합과 상한 검증을 통과한 것만 남는다.

### 대화 예시 (목표 품질)

```
코치: 오늘 하체 A 완료하셨네요! 어떠셨어요?
유저: 스쿼트 할 때 무릎이 좀 아팠어
코치: 무릎 통증은 그냥 넘기면 안 돼요. 얼마나 아팠어요?
      운동을 멈출 정도였나요, 아니면 살짝 불편한 정도?
유저: 살짝 불편한 정도? 근데 계속 신경쓰이긴 했어
코치: 알려주셔서 다행이에요. 다음부터 스쿼트 대신 레그프레스로
      바꿔볼게요 — 무릎 부담이 훨씬 적고 같은 허벅지 운동이에요.
      무릎은 당분간 주의 부위로 기억해둘게요. 나머지는 괜찮았어요?
유저: 응 나머진 좋았어
코치: 좋아요, 정리해드릴게요 👇

  ┌─────────────────────────────────────┐
  │ 다음 운동부터 바뀌는 것              │
  │ · 스쿼트 → 레그프레스               │
  │   이유: 무릎 불편 신고. 부담이 적은  │
  │   대체 운동으로 같은 부위 유지       │
  │ · 무릎 → 주의 부위 등록             │
  │   이후 모든 루틴에서 자동 반영       │
  └─────────────────────────────────────┘
  통증이 계속되면 운동을 중단하고 전문가와 상담하세요.
```

마지막 카드가 `finalize_revision`의 출력이다. **변경 + 이유가 항상 쌍으로** 나간다.

## 3. 반영 방식 — 루틴이 실제로 바뀌는 규칙

| 규칙 | 내용 | 왜 |
|---|---|---|
| 새 버전 생성 | 기존 루틴을 고치지 않고 `FEEDBACK` 버전을 새로 만듦 | 이미 완료한 Day 기록이 어긋나지 않게 |
| 다음 운동부터 적용 | 완료한 Day 는 그대로, 남은 Day 만 새 버전으로 | 사용자 체감상 "다음부터 바뀜" |
| 통증은 즉시 | `SEVERE` 통증 → 금기 등록은 대화 중 바로 | 안전은 버전을 기다리지 않는다 |
| 변경 이력 보존 | 무엇을·왜 바꿨는지 `routine_revision` 에 전부 기록 | "왜 바뀌었지?" 화면 + 되돌리기 근거 |
| 대화 실패 대비 | 채팅이 죽어도 기존 한 방 피드백(텍스트 1건 → 해석)으로 폴백 | 피드백 루프가 끊기지 않게 |

## 4. 구현 난이도 — 정직한 평가

**이미 있는 것 (전체의 ~70%)**

| 부품 | 상태 |
|---|---|
| Function Calling 도구 3종 + 해석 파이프라인 | ✅ 구현·머지됨 |
| 운동 후보 집합 + 교체 검증 | ✅ F10 에서 그대로 재사용 |
| 볼륨 상한 3중 검증 + 회귀 테스트 | ✅ `verify_routine_rules.py` |
| 금기 세션 누적 | ✅ 동작 중 |
| 변경 이력 (`routine_revision`) | ✅ 동작 중 |
| 버전 생성 (`FEEDBACK` 타입) | ✅ 스키마·정책 있음 |

**새로 만드는 것 (~30%)**

| 작업 | 난이도 | 내용 |
|---|---|---|
| 대화 API (동기) | 중 | `POST .../chat` — 잡 큐가 아니라 즉답. 메시지 저장 테이블 1개 (A 협의) |
| 코치 프롬프트 | 중 | 페르소나 + 오늘의 루틴·진단·금기 컨텍스트 주입 + 도구 사용 규칙 |
| 대화 종료 판정 | **상** | 언제 `finalize_revision` 을 부를지 — 제일 어려운 지점 |
| 턴·비용 제한 | 하 | 최대 8턴, 초과 시 자동 마무리 |
| 프론트 채팅 UI | 중 | 채팅창 + 마지막 요약 카드 (프론트 작업) |

**어려운 건 채팅 자체가 아니라 "끝내는 것"이다.** 대화가 늘어지거나, 주제가 새거나
(식단 질문 등), 사용자가 답을 안 하고 나가는 경우를 전부 안전하게 닫아야 한다.
대응: ① 최대 8턴 후 자동 요약 ② 주제 밖 질문은 한 줄 답변 후 복귀 ③ 이탈 시
그때까지 합의된 변경만 적용 (없으면 무변경).

**예상 규모**: 백엔드 2~3일 + 프론트 채팅 UI. 해커톤 데모 임팩트 대비 합리적.

## 5. 조사 결과 — 데이터셋·라이브러리·참고 연구

### 결론 먼저

> **파인튜닝용 한국어 코칭 대화 데이터셋은 사실상 없다. 그리고 필요 없다.**
> 이 분야 최신 연구들도 파인튜닝이 아니라 **프롬프트 전략 + 도구 제약**으로
> 만들었다 — 우리가 이미 쓰고 있는 방식이다.

### 참고 연구 (프롬프트 설계에 직접 활용)

| 자료 | 뭐가 유용한가 |
|---|---|
| **GPTCoach** (Stanford, CHI 2025) — [논문](https://arxiv.org/html/2405.06061v2) · [코드 공개](https://dl.acm.org/doi/10.1145/3706598.3713819) | 운동 코칭 챗봇의 표준. **동기부여 면담(Motivational Interviewing) 대화 전략**을 프롬프트로 구현 — "지시하지 말고 끌어내라". 도구 사용 구조도 우리와 동일. 코치 페르소나 프롬프트를 이걸 참고해 쓴다 |
| **PlanFitting** (KAIST) — [논문](https://arxiv.org/pdf/2309.12555) | LLM 대화로 운동 계획을 함께 세우는 연구. **사용자 제약(시간·장비·선호)을 대화에서 추출해 계획에 반영**하는 흐름이 우리 ⑤단계와 같다 |
| **QEVD FIT-COACH** — [논문](https://arxiv.org/html/2407.08101) | 실시간 영상 코칭 벤치마크. 지금 범위 밖이지만 "언제 말할지"의 참고 |
| **ChatCoach** — [논문](https://arxiv.org/pdf/2402.05547) | 코칭 대화 데이터가 없을 때 **멀티 에이전트로 합성 대화를 만들어 검증**하는 방법. 우리 테스트 데이터 생성에 쓸 수 있다 |

### 도구·라이브러리

| 도구 | 용도 | 판단 |
|---|---|---|
| **OpenAI Function Calling** | 대화 중 도구 호출 | ✅ 이미 사용 중. 추가 도입 없음 |
| **DeepEval** — [멀티턴 시뮬레이션](https://deepeval.com/guides/guides-multi-turn-simulation) · [대화 평가](https://deepeval.com/docs/metrics-conversational-g-eval) | **가상 사용자로 대화를 자동 시뮬레이션**해서 회귀 테스트. "무릎 아픈 사용자" 시나리오를 코드로 정의하면 프롬프트 바꿀 때마다 자동 검증 | ✅ 도입 권장 — 대화형의 최대 리스크(프롬프트 수정이 조용히 품질을 깨는 것)를 잡는 유일한 방법 |
| promptfoo | 레드팀·취약점 스캔 | 보류 — 해커톤 범위 밖 |
| LangChain / LangGraph | 대화 오케스트레이션 | ❌ 미도입 — 8턴 단일 대화에 프레임워크는 과함. 의존성만 는다 |
| [AI Hub 한국어 대화 데이터](https://aihub.or.kr/aihubdata/data/view.do?dataSetSn=272) | 한국어 파인튜닝 | ❌ 운동 코칭 대화는 없음 (피트니스 자세 데이터뿐). 파인튜닝 자체가 불필요 |

### 우리 데이터가 자산이 된다

`routine_revision` 에 대화 전문·변경·이유가 쌓인다. 서비스가 크면 **이게 곧
한국어 운동 코칭 대화 데이터셋**이다 — 지금 없는 그 데이터를 우리가 만들게 된다.

## 7. 요약 — 한 문장씩

- **무엇**: 운동 끝난 날 코치와 대화 → 대화 끝에 "바뀐 루틴 + 이유" 카드
- **어떻게**: 말은 자유, 행동은 검증된 도구 4개 — 대화가 새도 루틴은 안 망가진다
- **반영**: 다음 운동부터 새 버전으로, 통증만 즉시
- **난이도**: 부품 70%가 이미 있음. 어려운 건 대화를 "잘 끝내는" 설계
- **데이터셋**: 필요 없음이 결론. Stanford GPTCoach 프롬프트 전략 + DeepEval 시뮬레이션 테스트로 품질 확보
