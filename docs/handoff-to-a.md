## 1. 🔴 의류 병합은 A 파이프라인에서 — `is_valid` 판정 **이전** (필독)

### 배경 — PM 확정 (2026-08-13)

| 확정 | 내용 |
|---|---|
| 레퍼런스 | 몸 전반이 잘 보이는 이미지로 고정 |
| 사용자 사진 | 신뢰도 평가 → 미달이면 재촬영 유도 |
| 인바디 | 1건 넣는 것으로 가정 (옷을 입어도 루틴 추천 성립) |
| **촬영 통과 후** | **상·하의 클래스를 몸에 병합해 전 부위 비교** |

### 문제 — 순서가 뒤집혀 있으면 병합이 무의미해집니다

```
현재 순서:  세그 → 부위별 통계 → is_valid 판정(병합 전 픽셀) → DB
그 뒤 B가 병합:  이미 TOO_SMALL 로 걸러진 부위는 되살릴 수 없음
```

**실측 시뮬레이션** (A 제공 샘플 기준, `seg_min_pixels=1500`):

| 상황 | 상완 픽셀 | 판정 |
|---|---|---|
| 반팔 (현재 샘플) | 8,107 | 유효 |
| 긴팔, 노출 30% 가정 | 2,432 | 유효 |
| 긴팔, 노출 15% 가정 | 1,216 | ❌ `TOO_SMALL` |

병합하면 살아나는 부위가 **판정 순서 때문에** 죽습니다.

### 요청

**맵 후처리로 픽셀 자체를 리매핑**해 주세요. `is_valid` 판정 이전에요.

```
Upper_Clothing(23) → Torso(22)
Lower_Clothing(13) → 좌/우 허벅지로 분배
Apparel(1)         → 무시 (모자·장갑 등)
```

이러면 부위별 통계 · `is_valid` · B의 하이라이트 · 프론트 오버레이가 **전부 같은 맵**을
보게 되어 병합 로직이 한 곳에만 존재합니다. B가 마스크 단계에서 따로 병합하면 구현이
두 벌이 되어 언젠가 어긋납니다.

**`Lower_Clothing` 좌우 분배** — A 샘플로 검증했습니다. 좌우 허벅지 경계선으로 나뉩니다.

```
Right_Upper_Leg x: 205~370
Left_Upper_Leg  x: 368~482      → 경계 x≈369
Lower_Clothing 8,848px → 왼쪽 5,913 / 오른쪽 2,935
결과: Left +34%, Right +15%   (비대칭은 다리를 벌린 자세 때문)
```

구현 방식은 A 재량입니다. **위치(= `is_valid` 판정 이전)만 지켜지면 됩니다.**

### 참고 — 이 병합은 생각보다 자주 no-op 입니다

A 샘플(몸에 붙는 상의) 실측:

| 클래스 | 픽셀 |
|---|---|
| `Upper_Clothing` (23) | **0** |
| `Lower_Clothing` (13) | 8,848 |
| `Torso` (22) | 48,175 |

오버레이를 렌더링해 보니 Torso 실루엣이 **명백히 셔츠 모양**(라운드넥·암홀·수평 밑단)
이었습니다. Sapiens2가 붙는 상의를 Torso로 흡수하는 것으로 보입니다.
→ **확인 요청**: 그 인물이 상의를 입고 있었나요? 맞다면 상의 병합은 헐렁한 옷 대비
안전망이고, 실질 효과는 `Lower_Clothing` 쪽이 큽니다.

## 2. `SEG_USER` job.result 에 `retake_recommended` 추가 요청

재촬영 유도(PM 확정 2번)에 필요한 부품은 이미 A가 다 만들어 두셨습니다.
포즈 게이트(동기) + `valid_comparable`(비동기) + `min_comparable_parts=3`.

플래그 하나만 서버가 내려주면 프론트가 임계값을 몰라도 됩니다.

```json
{
  "valid_comparable": 2,
  "retake_recommended": true,
  "invalid": [{"class_name": "Left_Upper_Arm", "reason": "TOO_SMALL"}]
}
```

`pose.py`의 **"측정은 프론트, 정책은 서버"** 규약과 같은 취지입니다.

⚠️ 이 판정도 **병합 후** 픽셀 기준이어야 합니다 (§1과 같은 이유).

## 3. 맵 샘플 검증 완료 — 함정 2개 확인했습니다

주신 샘플로 하이라이트 파이프라인을 검증했습니다 (`scripts/verify_segmap.py`, 20/20 통과).
알려주신 주의사항 두 개 모두 실측으로 재현했습니다.

| 항목 | 실측 |
|---|---|
| 종횡비 | `sx=0.9115` `sy=1.0244` (11% 차이). 단일 배율이면 Torso bbox 가로 **31px** 어긋남 |
| 보간 | BILINEAR 시 라벨 종류 23 → **28**. 없던 `Apparel`·`Eyeglasses`·`Upper_Clothing`·`Sock` 생성 |
| 픽셀 수 | 9개 부위 전부 `segmentation.json`과 정확히 일치 |
| bbox | Torso 실측 `x=272 y=219 w=227 h=289` — 명세와 완전 일치 |
| 좌우 | 인물 왼팔이 화면 오른쪽 ✓ |

`segmap.resize_mask()`는 보간을 인자로 빼지 않고 NEAREST 로 고정했습니다.
선택 가능하게 두면 언젠가 누가 바꾸고, 그러면 조용히 틀립니다.

## 4. 지난 회신에 대한 답

### 좀비 잡 타임아웃 — 900초로 충분합니다

B 쪽 가장 긴 호출이 루틴 생성 1회(1주치, 수십 초)입니다. VLM 부위별은 9개가 각각
별도 잡이라 잡 하나당 API 호출 1회입니다. **15배 이상 여유가 있어 변경 요청 없습니다.**

`find_open()` + `reclaim_stale()` 2단 설계가 제가 제안한 `claim()` 단독 수정보다
낫습니다 — 재시도를 소진한 좀비가 `PROCESSING`에 영구히 남아 화면이 "실패"조차
못 띄우는 구멍을 짚어주신 게 정확했습니다.

### 상완/전완 비율 — 제 가정이 틀렸고, 기준을 다시 잡지 않습니다

```
Left  8,107 / 5,482 = 1.48
Right 9,063 / 5,188 = 1.75
```

제 기준(1.1~1.3)이면 이 정상 사진도 오판입니다. 상완 세그먼트에 삼각근이 포함되고
전완은 아래로 갈수록 가늘어진다는 걸 간과했습니다.

다만 **n=1로 새 임계값을 잡지는 않겠습니다.** `clothing_ratio > 0.5` 때와 같은 실수가
됩니다. 게다가 이번에 `Upper_Clothing` 검출 자체가 불안정하다는 게 드러나 픽셀 기반
가림 추론은 근거가 더 약해졌습니다. **휴리스틱 자체를 폐기**하고 가림 판정은 VLM
자기신고 하나로 갑니다.

→ `TOO_SMALL` 로직은 **그대로 유지**해 주세요. 임계값 조정 시에만 알려주시면 됩니다.

### `_load_handlers` importlib 수정 — 확인했습니다

`vlm`/`routine` 부재 상태에서 `OCR_INBODY`만 정상 등록되는 것 실측 확인했습니다.
그 버그 없었으면 제가 곧 밟았을 자리 맞습니다. 잡아주셔서 감사합니다.

### PRESET 미도입 — B 코드 영향 없습니다

`reference_source`를 읽는 B 코드는 0줄입니다.
프론트가 `valid_comparable < 3`으로 레퍼런스 단계에서 거르는 방안도 좋습니다.
