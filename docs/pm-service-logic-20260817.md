# REFIT — STEP 1~3 흐름과 운동 추천 로직

**PM 전달용** · 2026-08-17
어떤 정보를 뽑아 → 어디로 넘기고 → 무엇의 근거로 쓰는지, **다리(hop) 단위**로 정리했습니다.

---

## 0. 먼저, 전체 그림 한 장

```
[브라우저]                [API 서버]           [워커]              [외부 모델]
   │                         │                  │                    │
   │ ① 사진 2장 + 관절좌표    │                  │                    │
   ├────────────────────────>│                  │                    │
   │                         │ 일감 등록         │                    │
   │                         ├─────────────────>│ 사진 꺼내서        │
   │                         │                  ├───────────────────>│ Sapiens2
   │                         │                  │<───────────────────┤ (부위 分割)
   │                         │                  │ 부위 통계 저장      │
   │                         │                  ├───────────────────>│ GPT-4o
   │                         │                  │<───────────────────┤ (진단 문장)
   │ ② "다 됐어?" 물어봄      │                  │ 결과 저장          │
   ├────────────────────────>│                  │                    │
   │<────────────────────────┤ 진단 + 점수      │                    │
```

**핵심 구조 두 가지**

1. **무거운 작업은 서버가 바로 하지 않습니다.** 일감(Job)으로 등록해두고 워커가
   가져가 처리합니다. 사진 분석은 30~90초 걸려서, 기다리게 하면 요청이 끊깁니다.
   화면은 "다 됐어?"를 주기적으로 물어봅니다.
2. **AI 모델은 두 종류를 씁니다.** 서로 하는 일이 완전히 다릅니다.

| 모델 | 하는 일 | 어디서 도나 |
|---|---|---|
| **MediaPipe** | 관절 33점 찾기 | **사용자 브라우저** (서버 안 감) |
| **Sapiens2** | 몸을 부위별로 잘라내기 (픽셀 단위) | 워커 (GPU) |
| **GPT-4o** | 인바디 읽기 · 진단 문장 · 운동 선택 | OpenAI API |

# STEP 1 — 목표 체형 사진

> "어디로 가고 싶은가"의 기준점을 만드는 단계

### 다리 1 — 브라우저에서 먼저 걸러냅니다

```
사진 선택
  └─> [브라우저] MediaPipe 실행 → 관절 33점 좌표
        └─> 사람이 안 잡히면? 여기서 반려. 서버에 안 보냄
```

**왜 브라우저에서 하나**: 못 쓸 사진을 서버까지 보내고 기다렸다 반려하면
사용자가 30초를 버립니다. 관절 검출은 브라우저에서 1초 안에 끝납니다.

### 다리 2 — 서버로 올라갑니다

```
[브라우저] ──> [API 서버]
             사진 파일 + 관절좌표 + 촬영 메타
                └─> Storage에 원본 저장
                └─> "이 사진 분석해줘" 일감 등록 (SEG_REFERENCE)
                └─> 즉시 응답 (기다리지 않음)
```

### 다리 3 — 워커가 Sapiens2를 돌립니다

```
[워커] 일감 꺼냄
  └─> Storage에서 사진 다운로드
  └─> Sapiens2 실행 ──> 픽셀마다 "이건 몸통, 이건 왼팔" 라벨링 (29종)
        └─> 부위별 픽셀 수 · 위치 · 면적 비율 계산
        └─> DB에 저장 + 라벨 맵 이미지 저장
```

**뽑히는 정보**

| 정보 | 이후 어디에 쓰이나 |
|---|---|
| 관절 33점 | STEP 2의 포즈 일치 판정 기준 |
| 부위별 픽셀 영역 | 부위 비교의 "목표" 쪽 |
| 부위별 유효성 | 옷에 가렸거나 잘린 부위를 진단에서 제외 |

> ⚠️ **이 사진에 없는 부위는 끝까지 개인화되지 않습니다.** 그래서 업로드 전에
> "이 레퍼런스에 있는 부위에 대한 루틴만 제공된다"고 미리 고지합니다.

# STEP 2 — 내 체형 사진

> "지금 어디인가" — **포즈가 같아야 비교가 성립합니다**

### 왜 포즈를 맞추게 하나

사람 몸은 각도가 조금만 틀어져도 실루엣이 크게 달라집니다.
특히 **팔을 몸에 붙이면 팔이 아예 검출되지 않아** 진단에서 통째로 빠집니다.

### 다리 1 — 브라우저가 실시간으로 판정합니다

```
카메라 켜짐
  └─> [브라우저] 매 프레임 MediaPipe → 관절 33점
        └─> 레퍼런스 관절과 비교 → 점수 계산 (전부 브라우저에서)
              └─> 기준 통과가 약 1초 유지되면 → 자동 촬영
```

**판정 항목 3가지** (기준 수치는 서버가 내려주고 화면이 그대로 씁니다 —
하드코딩하면 서버에서 조정해도 화면이 안 따라옵니다)

| 항목 | 보는 것 | 통과 기준 |
|---|---|---|
| 포즈 유사도 | 관절 각도 8개가 레퍼런스와 같은가 | 70점 |
| 촬영 거리 | 몸통 길이 비율 (멀면 부위가 작게 잡혀 무효) | — |
| 레퍼런스 커버리지 | 레퍼런스에 보이는 부위가 내 사진에도 보이는가 | 70% |

> ⚠️ **거울 처리**: 셀피 미리보기는 좌우가 뒤집힌 거울입니다. 화면에 보이는 대로
> 따라 하면 해부학적으로 **반대 관절**을 쓰게 됩니다. 그래서 판정할 때
> 레퍼런스를 좌우 반전해서 비교합니다. 규칙은 하나 — **판정 방향 = 화면 방향.**

### 다리 2~3 — STEP 1과 동일

서버 업로드 → 일감 등록(SEG_USER) → 워커가 Sapiens2 실행.
서버도 브라우저가 보낸 점수를 **다시 검증**합니다 (브라우저 값은 신뢰하지 않음).

# STEP 3 — 인바디 결과지 (선택)

> **없어도 서비스는 끝까지 완주합니다.** 있으면 사진이 못 보는 것을 채웁니다.

### 다리 1~2 — 사진 업로드 → GPT-4o가 읽음

```
결과지 사진
  └─> [API 서버] Storage 저장 + 일감 등록 (OCR_INBODY)
        └─> [워커] ──> GPT-4o (Vision) ──> 수치를 JSON으로 추출
              └─> [코드] 검증 ← 여기가 중요
```

### 다리 3 — 코드가 AI의 추출값을 검증합니다

AI가 숫자를 잘못 읽을 수 있으므로, **물리적으로 성립하는지** 코드가 확인합니다.

- **항등식 검사**: 체중 = 체지방량 + 제지방량 (오차 3% 이내인가)
- **범위 검사**: 체지방률 1~70%, 기초대사량 500~5000kcal 등
- **좌우 대칭 검사**: 좌우 근육량 차이 30% 넘으면 경고 (자동 수정은 안 함)

검증에 걸리면 **사용자에게 보여주고 직접 고치게 합니다.** AI가 조용히
고치지 않습니다 — 틀린 값으로 진단이 나가는 것보다 낫습니다.

### 인바디를 어디에 쓰고 어디에 안 쓰는가 — **가장 중요한 설계 판단**

기준선이 **두 개**입니다. 섞으면 진단이 무너집니다.

|  | 답하는 질문 |
|---|---|
| **사진 비교** | 내가 **목표 체형과** 얼마나 다른가 |
| **인바디 "표준 대비 %"** | 내가 **일반인 평균과** 얼마나 다른가 |

평균 수준(90~100%)이어도 목표가 근육질이면 격차는 큽니다.
인바디로 등급을 매기면 **모든 부위가 '약간 부족'으로 눌립니다.**

> **그래서: 부위 등급은 언제나 이미지가 정합니다.**

인바디는 세 곳에만 씁니다:

1. 현재 상태를 설명하는 **보조 수치** (인용할 때 '평균 대비'임을 밝힘)
2. **좌우 근육량 비교** — 같은 사람의 실측이라 픽셀보다 신뢰도가 높음
3. **옷에 가린 부위**의 유일한 근거

별도로 **감량 병행 여부(CUT/BALANCE)** 판정에 체지방률을 씁니다.
이건 "목표와의 격차"가 아니라 건강 지표라 기준선이 달라도 됩니다.

# 진단 — 두 사진을 부위별로 비교

### 다리 1 — 워커가 GPT-4o에 넘길 재료를 만듭니다

여기가 **"사피엔스2 → OpenAI" 다리**입니다.

```
[워커]
  ├─ 레퍼런스 사진 (원본, 긴 변 축소)
  ├─ 레퍼런스 오버레이 ← Sapiens2 라벨 맵으로 부위마다 색칠한 그림
  ├─ 내 사진 (원본, 긴 변 축소)
  ├─ 내 오버레이 ← 같은 방식
  ├─ 부위별 수치 (픽셀 수, 면적 비율, 좌우 대칭, 옷 흡수 비율, 잘림 여부)
  └─ 인바디 수치 (제출했으면)
        │
        └──> GPT-4o ──> 부위 9개 진단 JSON
```

**색칠한 그림을 같이 보내는 이유**: 그냥 사진만 주면 "왼쪽 상완"이 어디인지
모델이 자기 마음대로 정합니다. Sapiens2가 잘라낸 영역을 색으로 찍어주면
**수치와 그림이 같은 몸을 가리킵니다.**

### 다리 2 — AI가 문장을 쓰고, 코드가 점수를 냅니다

```
GPT-4o  →  부위별 등급 + 진단 문장
   │
   └──> [코드] 검증
          ├─ 근거 없는 서술 차단
          ├─ 좌우 문장 통일 (실측 차이가 3% 안쪽이면 다르게 쓸 재료가 없음)
          └─ 점수 계산 ← AI가 보낸 점수는 버림
```

**유사도 점수 산식**

```
등급별 점수:  차이 없음 100 │ 약간 75 │ 보통 50 │ 큼 25
전체 점수  :  판단된 부위들의 평균
```

> **AI가 점수를 보내와도 버립니다.** 같은 진단이면 항상 같은 점수가 나와야
> 하기 때문입니다. AI에게 점수를 맡기면 같은 사진에 매번 다른 점수가 나옵니다.

**비교 대상 9개**: 몸통 · 좌우 상완 · 좌우 전완 · 좌우 허벅지 · 좌우 종아리
(얼굴·손·발은 비교 대상 아님)

**부위가 빠지는 경우**: 옷에 가려 너무 작거나, 화면에서 잘렸거나, 두 사진 중
한쪽에만 보일 때. **빠진 이유를 화면에 표시합니다** —
"몸통이 거의 보이지 않습니다. 옷에 가려졌을 수 있어요."

# 운동 추천 — 6단계, AI는 딱 1번만 개입

```
① 모드 판정    [코드]  체지방률 → CUT(감량 병행) / BALANCE(기본)
② 골격 짜기    [코드]  주 N일 분할, 슬롯별 세트·횟수 ← 가이드라인
③ 약점 가중    [코드]  우선 부위에 +1세트씩 (3중 상한)
④ 후보 추리기  [코드]  각 슬롯에 맞는 운동만 카탈로그에서 필터
⑤ 종목 선택    [AI]    ★ 후보 안에서 고르기만
⑥ 검증·조립    [코드]  후보 밖 응답 폐기 → 1순위 대체, RIR 부여
```

### 왜 이렇게 쪼갰나

**AI가 없는 운동을 지어내도 사용자에게 도달할 수 없습니다.** 후보 목록 밖의
응답은 코드가 버리고 1순위로 대체합니다.

**AI 호출이 실패해도 루틴은 나옵니다.** 후보 순서대로 기계적으로 고르는
경로가 있어서, 어떤 상황에서도 루틴 생성은 실패하지 않습니다.

### 진단이 루틴에 반영되는 방식

> ⚠️ **진단은 운동을 넣고 빼지 않습니다. 볼륨 가중치로만 작용합니다.**

진단이 없거나 실패한 부위도 **기본 볼륨을 그대로 받습니다.**
기본 볼륨의 근거는 진단이 아니라 가이드라인이기 때문입니다.
진단이 하는 일은 "약한 곳에 세트를 조금 더 얹는 것"까지입니다.

가중에는 **3중 상한**이 걸립니다 (근육군당 가산 / 근육군 주간 총량 / 슬롯당 세트).
"약점이니까 무한정 더"가 되지 않게 하는 안전장치입니다.

### 루틴의 단위

**요일이 아니라 "주기당 N일"입니다.** N = 사용자가 고른 1~7일, 4주기 반복.
휴식일 행이 없습니다.

사용자가 이틀 연속으로 할 수 있으므로 **인접 Day가 같은 근육군을 반복하지 않게**
배치합니다 (상체 → 하체 → 상체).

진행도는 **날짜가 아니라 완료 횟수**로 셉니다 — 하루 밀려도 계획이 깨지지 않게.

# 수치의 근거 — 논문을 실제로 어떻게 적용했나

> 아래 수치는 전부 코드 주석에 출처가 명기되어 있습니다
> (`app/services/routine_templates.py` 상단 "수치의 출처").

### ① 분할 구조 — ACSM 2009 Position Stand (PMID 19204579)

*Progression Models in Resistance Training for Healthy Adults*

**논문이 말하는 것**: 초보자는 전신 운동 주 2~3일. 부위를 나누는 분할 훈련은
주 4일 이상부터 의미가 있다.

**코드에 어떻게 들어갔나**: 사용자가 고른 일수로 템플릿이 갈립니다.

```
1~3일 선택 → 전신 A / B / C (구성을 달리해 주동근이 겹치지 않게)
4일+ 선택  → 상하체 분할
```

### ② 세트·횟수 — 같은 ACSM 문서

**논문이 말하는 것**: 초보자 1~3세트 × 8~12회. 근지구력 목적은 15~25회.

**코드에 어떻게 들어갔나**: 슬롯별 기본 세트·횟수가 이 범위 안에서 고정입니다.
코어·종아리만 15회 (근지구력 범위).
**AI는 이 숫자를 건드리지 못합니다** — 종목만 고릅니다.

### ③ 주 몇 회 할지 — Schoenfeld 2019 (PMID 30558493)

**논문이 말하는 것**: **총 볼륨이 같으면 주당 빈도는 결과에 영향이 없다.**

**코드에 어떻게 들어갔나**: 이 논문이 **"일수를 사용자가 고르게 해도 된다"의
근거**입니다. 주 2일이든 5일이든 총 볼륨만 맞추면 되므로,
일수는 사용자 편의로 두고 **볼륨 배분은 코드가 책임집니다.**

### ④ 볼륨 상한 — Schoenfeld 2017 (PMID 27433992)

**논문이 말하는 것**: 주당 세트 수와 근비대는 용량-반응 관계 (~10세트/주 기준).

**코드에 어떻게 들어갔나**: 약점 가중이 무한정 쌓이지 않도록
**근육군당 주간 총 세트 상한**으로 씁니다.

> ⚠️ 이건 생리학적 절대 상한이 아닙니다. "초보자에게 과하지 않게"라는
> 안전 기준으로 쓰는 값이고, 코드 주석에도 그렇게 적혀 있습니다.

### ⑤ 무게 처방 — Zourdos 2016 (RIR 척도)

**논문이 말하는 것**: RIR(Reps In Reserve) = "몇 회 더 할 수 있는가"로
강도를 자가조절하는 척도.

**코드에 어떻게 들어갔나**: 모든 근력 운동에 **RIR 2**를 붙입니다.
화면 문구: *"10회를 마쳤을 때 2회 정도 여유가 남는 무게로 하세요."*

**이 논문이 없앤 기능이 있습니다**: 원래 "1주차 대비 2주차 +10%" 같은
주차별 배율을 넣으려 했는데 **폐기했습니다.** RIR 자가조절 자체가 점진 과부하를
내장하기 때문입니다 — "2회 남기고 멈추는 무게"는 능력이 오르면 저절로 올라갑니다.

**무게를 kg로 처방하지 않는 이유도 여기입니다.** 1RM 측정 없이 kg를 제시하면
부상 위험이 있습니다. RIR은 근거 있는 회피 수단입니다.

### ⑥ 유산소 — ACSM Donnelly 2009

**논문이 말하는 것**: 체중 감량에는 주 150분 이상의 중강도 유산소가 필요.

**코드에 어떻게 들어갔나**: CUT 모드일 때 근력일마다 유산소 15~20분을 붙입니다.

> ⚠️ **정확히 해둘 것**: 루틴이 주 150분을 보장하지 **않습니다.**
> 주 3일이면 루틴이 주는 건 45분뿐입니다. 나머지는 일상 활동·걷기 안내로
> 분리했고, **"주간 활동량을 점진적으로 늘린다"가 실제 처방**입니다.
> 논문 수치를 그대로 가져다 "우리가 150분 준다"고 말하지 않았습니다.
