---

## 무엇을 판단하는 건가

**"이 두 사진을 부위별로 견줘도 되는가"** 입니다. 사진의 잘잘못이 아닙니다.

레퍼런스는 팔을 내리고 있는데 사용자가 팔을 벌리고 있으면, 상완의 보이는 면적이
달라져서 **"팔이 굵다/가늘다"를 비교할 수 없습니다.** 자세가 결과를 오염시킵니다.

---

## ⚠️ 좌표를 직접 비교하면 안 되는 이유

사용자가 레퍼런스보다 **한 발 뒤에 서 있으면** 모든 좌표가 달라집니다. 하지만
자세는 똑같습니다. 좌표 차이로 점수를 매기면 **자세가 아니라 서 있는 위치를 재게 됩니다.**

그래서 세 가지를 따로 잽니다.

| | 무엇을 | 왜 필요한가 | 무엇에 불변인가 |
|---|---|---|---|
| **P** 자세 | 관절이 이루는 **각도** | 팔다리가 같은 방향인가 | 위치·거리·사람 크기 |
| **F** 프레이밍 | 인물이 화면을 채우는 **모양** | 둘 다 전신이 비슷하게 담겼나 | — |
| **R** 몸통 방향 | 어깨폭 / 몸통길이 **비율** | 레퍼런스와 같은 방향인가 | 위치·거리 |

**R이 왜 따로 있는가** — 팔을 내린 자세는 정면이든 30° 돌아섰든 **각도가 거의 같습니다.**
그런데 몸이 돌아가면 어깨폭이 좁아 보여서, 정작 우리가 진단하는 **실루엣 굵기가 왜곡됩니다.**
각도만으로는 이걸 못 잡습니다.

> ⚠️ **R은 2026-08-14부터 관찰용입니다. 판정에 쓰지 않습니다.**
> 어깨폭 비율이 잡음에 민감해 육안으로 비슷한 자세를 반복해서 반려했습니다.
> 값은 계속 계산·저장합니다 — "돌아간 사진이 진단을 실제로 얼마나 망치나"가
> 데이터로 쌓이면 관문을 되살릴 수 있습니다. 자세한 사정은 아래 R 절 참고.

## P — 자세 유사도 (0~100)

### 재는 각도 9개

부위별 진단 대상과 정확히 대응시킵니다. **비교하지 않을 부위의 각도는 재지 않습니다** —
얼굴 방향이 다르다고 자세가 틀렸다고 할 이유가 없습니다.

| 각도 | 랜드마크 | 대응 진단 부위 |
|---|---|---|
| 왼쪽 상완 | 어깨(11) → 팔꿈치(13) | 왼팔 상완 |
| 왼쪽 전완 | 팔꿈치(13) → 손목(15) | 왼팔 전완 |
| 오른쪽 상완 | 어깨(12) → 팔꿈치(14) | 오른팔 상완 |
| 오른쪽 전완 | 팔꿈치(14) → 손목(16) | 오른팔 전완 |
| 왼쪽 허벅지 | 엉덩이(23) → 무릎(25) | 왼쪽 허벅지 |
| 왼쪽 종아리 | 무릎(25) → 발목(27) | 왼쪽 종아리 |
| 오른쪽 허벅지 | 엉덩이(24) → 무릎(26) | 오른쪽 허벅지 |
| 오른쪽 종아리 | 무릎(26) → 발목(28) | 오른쪽 종아리 |
| 몸통 기울기 | 어깨중점 → 엉덩이중점 | 몸통 |

### 계산

각 각도의 **차이 `d`(도)** 를 구하고, 관절 하나의 점수를 이렇게 냅니다.

```
s = clamp(1 − d / TOL, 0, 1)        TOL = 60°
P = 100 × (s 들의 평균)
```

**평균을 쓰되, 한 관절이라도 크게 어긋나면 무조건 탈락시킵니다.**

```
어느 하나라도 d > HARD 이면  →  P = 0        HARD = 70°
```

> ⚠️ **평균만 쓰면** 왼팔이 완전히 다른 방향인데 나머지가 잘 맞아 통과합니다.
> 그러면 왼팔 진단만 조용히 틀립니다.
> **최솟값만 쓰면** 손목이 살짝 흔들린 것 때문에 전체가 탈락합니다.
> 그래서 둘을 같이 씁니다 — 평균으로 점수를 내고, 하드 상한으로 파국을 막습니다.

### ⚠️ 카메라 쪽으로 뻗은(단축된) 세그먼트는 뺍니다 (2026-08-14)

팔이 렌즈를 향하면 **투영 길이가 짧아지고, 그 2D 각도는 사실상 난수입니다.**
자세가 같아도 이 각도가 HARD를 넘겨 **전체를 0점으로 만들었습니다** —
"육안으로 같은데 안 찍히는" 제1 원인이었습니다.

```
세그먼트의 투영 길이 < 몸통 길이 × MIN_SEG_RATIO 이면 → 그 각도는 계산에서 제외
MIN_SEG_RATIO = 0.25      (양쪽 사진 중 한쪽만 단축이어도 제외)
```

HARD를 60→70으로 올린 것도 같은 맥락입니다 — 예전 60°의 오발은 대부분 단축
잡음이었고, 그건 이제 이 컷이 막습니다. 하드 상한은 "잘 보이는 팔이 70° 넘게
딴 방향 = 육안으로도 딴 자세"라는 진짜 파국만 담당합니다. (90까지 열어봤더니
팔 하나가 명백히 딴 방향인데 통과했습니다 — 70이 실사용과 맞았습니다.)

### 신뢰도가 낮은 관절은 뺍니다

MediaPipe는 관절마다 `visibility`(0~1)를 줍니다. 가려진 관절은 좌표가 추측값이라
각도가 엉뚱하게 나옵니다. **양쪽 사진 모두에서 `visibility ≥ 0.5` 인 각도만** 계산에 넣습니다.

⚠️ 남은 각도가 **4개 미만이면 판정 불가**로 보고 재촬영을 권합니다. 두세 개로 낸
평균은 근거가 약합니다.

## F — 프레이밍 일치 (0~1)

```
비율 = 사용자 몸통 길이 / 레퍼런스 몸통 길이      (어깨중점 ~ 골반중점)
F    = min(비율, 1/비율)
```

**두 사진이 비슷한 거리에서 찍혔는가**만 봅니다. 1이면 같은 거리입니다.

⚠️ **예전에는 랜드마크 전체의 사각형 겹침(IoU)이었습니다. 그건 틀린 값이었습니다.**

팔다리를 움직이면 사각형이 같이 변합니다. 그래서 **자세가 다른 것을 프레이밍
문제로 보고했습니다.** 실측입니다 — 전신을 균일하게 틀었을 때:

| 회전 | 자세 점수 | 옛 F (사각형 IoU) | 먼저 걸리는 것 |
|---|---|---|---|
| 14° | 72.3 | 0.672 | — |
| 16° | 68.4 | 0.652 | 자세 |
| **20°** | 60.5 | **0.615** | **프레이밍** ← 잘못됨 |
| 30° | 40.7 | 0.539 | 프레이밍 ← 잘못됨 |

16°를 넘으면 사용자에게 **"몸이 화면에 다 나오도록 서주세요"** 가 뜹니다.
그런데 실제로 고쳐야 할 건 자세입니다. **아무리 뒤로 물러나도 통과하지 못합니다.**

⚠️ **위치는 보지 않습니다.** 사용자가 화면 왼쪽에 서든 오른쪽에 서든 굵기 비교에는
영향이 없습니다 — 부위 굵기를 몸통 길이로 정규화하기 때문입니다.
옛 방식은 옆으로 6%만 움직여도 0.58로 떨어져 거부했습니다.

**무엇을 막는가** — 레퍼런스는 전신인데 사용자는 바짝 붙어 찍은 경우.

| 상황 | 새 F | 판정 |
|---|---|---|
| 자세만 다름 | 1.000 | 통과 (프레이밍 문제 아님) |
| 옆으로 20% 이동 | 1.000 | 통과 (위치는 무관) |
| 20% 더 가까이 | 0.833 | 통과 (계산으로 보정됨) |
| **2배로 다가섬 (상반신만)** | **0.500** | **거부** |

⚠️ 어깨나 골반이 안 보이면 0입니다. 잴 기준이 없다는 뜻이고, 그때는
"몸이 화면에 다 나오도록"이 맞는 안내입니다.

## R — 몸통 방향 차이 (관찰용 — 판정에 쓰지 않음)

> ⚠️ **2026-08-14 — R 관문을 판정에서 뺐습니다** (서버 `judge_user_photo` 와
> 프론트 `evaluate` 동시). 어깨폭/몸통길이 비율이 자세·체형·검출 잡음에 민감해
> `R_MAX=0.25` 에서 육안으로 비슷한 자세를 반복 반려했습니다.
> 값은 계속 계산해 화면에 보여주고 DB에도 저장합니다. 반려 없이 쌓인 데이터로
> "몸이 돌아간 사진이 부위 비교를 실제로 망치는 선"을 실측하면, 그 선으로
> 관문을 되살립니다 (git 이력의 `pose_facing_max_delta`).
> 그전까지 90° 돌아간 사진의 방어는 2차 검사(VLM)가 맡습니다.

⚠️ **"정면인가"를 재는 값이 아닙니다.** 레퍼런스와의 **차이**입니다.

| 레퍼런스 | 사용자 | R |
|---|---|---|
| 정면 | 정면 | ≈ 0 |
| 정면 | 측면 | 0.5+ |
| **측면** | **측면** | **≈ 0** |

산식에 절대 기준이 없으므로 **측면·후면 레퍼런스도 그대로 동작합니다.**
안내 문구에 "정면"을 쓰면 안 되는 이유가 이것입니다 — 측면 레퍼런스를 쓰는
사용자가 올바르게 섰는데도 따라도 통과 못 하는 안내를 받게 됩니다.

⚠️ 다만 **실무적으로는 정면을 권합니다.** 측면은 반대쪽 팔다리가 가려 비교
가능 부위가 절반으로 줄고, 후면은 얼굴이 안 보여 MediaPipe 가 좌우를 뒤바꿀
수 있습니다(에러 없이). 레퍼런스 안내를 "정면 전신"으로 준 이유입니다.


```
비율 = 어깨 사이 거리 / 어깨중점~엉덩이중점 거리
R    = |비율(사용자) − 비율(레퍼런스)| / 비율(레퍼런스)

단, 반대쪽으로 돈 게 확실하면    R = (비율(사용자) + 비율(레퍼런스)) / 비율(레퍼런스)
```

몸이 돌아가면 어깨폭이 줄어들어 이 비율이 작아집니다. 몸통 길이로 나누기 때문에
**거리와 사람 크기에 영향받지 않습니다.**

### ⚠️ 왜 "반대쪽" 처리가 따로 필요한가

비율이 `cos θ`에 비례하는데 **`cos`는 좌우 대칭입니다.** 그래서 부호가 사라집니다.

| 레퍼런스 | 사용자 | 실제 차이 | 옛 R | 새 R |
|---|---|---|---|---|
| 0° | 30° | 30° | 0.134 | 0.134 |
| 0° | 45° | 45° | 0.293 | 0.293 |
| **+20°** | **−20°** | **40°** | **0.000** | **2.000** |
| **+45°** | **−45°** | **90°** | **0.000** | **2.000** |

**90° 어긋난 사람이 만점으로 통과하고 있었습니다.**

어느 쪽으로 돌았는지는 깊이(`z`)로 봅니다 — 어느 어깨가 카메라에 더 가까운지요.

⚠️ **MediaPipe의 `z`는 정밀도가 낮습니다.** 그래서 값이 아니라 **부호만**, 그것도
**회전 14° 이상일 때만** 씁니다. `atan`으로 각도를 뽑으면 매 프레임 흔들려 점수가 튑니다.
어중간하면 "모르겠다"로 두고 기존 계산을 그대로 씁니다.
`z`를 안 주는 구현이면 전부 "모르겠다"가 되어 **옛 동작 그대로**입니다.

⚠️ **그래서 R은 1을 넘을 수 있습니다.** 반대쪽으로 돌았을 때, 그리고 레퍼런스가
많이 돌아가 있어 분모가 작을 때요. **클램프하면 안 됩니다** —
서버 범위 검사도 이것 때문에 `0~1`에서 `0~10`으로 고쳤습니다
(10은 판정 기준이 아니라 단위 착오를 잡는 값입니다).

## 최종 판정

**안내와 거부를 나눕니다.** 자동 촬영(셔터) 조건은 거부선과 같습니다 —
서버가 받아줄 사진이면 찍습니다 (2026-08-14, 전에는 셔터만 F_MIN을 요구했습니다).

```
셔터 = 서버가 거부하지 않는 상태          서버가 거부하는 선
  유효 각도 ≥ 4개                        유효 각도 < 4개   → 거부
  F ≥ F_HARD                            F < F_HARD       → 거부
  P ≥ THRESHOLD                         P < THRESHOLD    → 거부

문구 안내만 (막지 않음)
  F < F_MIN  → "조금 뒤로/앞으로"
  R          → 관찰용 지표로 화면에 표시
```

⚠️ **F_MIN을 셔터 조건에서 뺀 이유** — 서버가 f_min으로 거부하지 않는데 셔터만
요구하면 "업로드는 되는데 자동 촬영은 안 되는" 사진이 생깁니다. 좁은 방에서는
f_min을 영영 못 넘기도 합니다 — 뒤로 가면 작아지고, 앞으로 오면 발이 잘립니다.
촬영 중 문구 안내는 공짜니 그대로 둡니다.

그리고 애초에 **거리 차이는 계산에서 상쇄됩니다.** 부위 굵기를 몸통 길이로
나눠 비교하므로, 2배 가까이 서면 팔뚝도 2배 몸통도 2배라 비율이 같습니다.
거리가 진짜 문제가 되는 두 경우는 각각 다른 곳이 잡습니다.

| 문제 | 잡는 곳 |
|---|---|
| 너무 가까워 원근이 왜곡됨 | 2차 검사 `PERSPECTIVE_MISMATCH` |
| 너무 멀어 픽셀이 부족함 | 부위별 `TOO_SMALL` |

`F_HARD`(0.40)를 남겨두는 이유는 **2차 검사가 실패하면 통과시키기 때문**입니다.
OpenAI가 죽었을 때 아무것도 안 걸러지는 상태는 피합니다.

⚠️ **순서가 의미를 갖습니다.** 프레이밍이 깨진 상태의 자세 점수는 믿을 수 없고,
안내 문구도 달라야 합니다 — "몸이 다 나오게 서주세요"와 "포즈를 맞춰주세요"는
사용자가 해야 할 행동이 다릅니다.

## 임계값과 그 근거

| 값 | 기본 | 근거 | 낮추면 / 높이면 |
|---|---|---|---|
| `TOL` | **60°** | 관절 하나가 0점이 되는 각도. 45°였는데, 사진을 보고 따라 서는 사람의 정밀도(관절당 15~25° 편차)에 맞춰 완화 | 낮추면 깐깐해져 재촬영이 잦음 |
| `HARD` | **70°** | 잘 보이는 팔이 이만큼 딴 방향이면 육안으로도 딴 자세. 예전 60°의 오발은 단축 잡음이었고(단축 컷이 해결), 90은 팔 하나가 명백히 딴 방향인데 통과시켰다 | — |
| `MIN_SEG_RATIO` | **0.25** | 투영 길이가 몸통의 ¼ 미만이면 카메라를 향해 뻗은 것 — 그 2D 각도는 난수라 뺀다 | 높이면 팔이 조금만 앞을 향해도 계산에서 빠짐 |
| `THRESHOLD` | **70** | `TOL=60` 기준 **평균 오차 18° 이내**. 55(평균 27°)는 조금만 비슷해도 찍혔고, 예전 70/TOL45(평균 13.5°)는 통과 불가에 가까웠다 — 실사용으로 맞춘 값 | 높이면 통과가 어려워짐 |
| `F_MIN` | **0.65** | **문구 안내용.** 거리 1.54배. 셔터·업로드 어느 쪽도 막지 않는다 | — |
| `F_HARD` | **0.40** | **거부용.** 거리 2.5배. 이쯤이면 다리가 화면 밖이라 어차피 못 쓴다 | 높이면 이탈이 늘어난다 |
| `R_MAX` | ~~0.25~~ | **제거됨 (2026-08-14).** R은 관찰용 — 위 R 절 참고 | — |
| `N_HOLD` | **30** | 셔터에 필요한 통과 프레임 수. 30fps 기준 **약 1초 유지** (2026-08-16, 10=0.3초는 너무 짧다는 판단). 연속이 아니라 **최근 39프레임(=N+30%) 중 30개** — lite 모델은 한 프레임씩 수시로 튀는데, 연속 조건은 그때마다 0부터 다시 셌다. 여유를 고정 3이 아니라 N의 30%로 두는 이유: 튐은 프레임당 확률이라 창이 길수록 절대 횟수가 는다 | — |

> ⚠️ **이 값들은 시작점입니다.** "논리적 타당성"은 숫자 자체가 아니라
> **(1) 산식이 거리·위치에 불변이고 (2) 각 임계값이 무엇을 막는지 말할 수 있고
> (3) 조정 방법이 정해져 있다**는 데 있습니다.
>
> **조정 방법** — 시연에 쓸 레퍼런스로 사람이 **일부러 잘 맞춘 사진 5장**과
> **일부러 다르게 찍은 사진 5장**을 찍어 점수를 뽑습니다. 두 무리 사이가
> 벌어지는 지점에 `THRESHOLD`를 놓습니다. 겹치면 `TOL`을 조정합니다.

## K — OKS (관찰용, 아직 판정에 안 씀)

`P`의 약점은 **`TOL=45°`에 근거가 없고, 관절을 전부 똑같이 취급한다**는 점입니다.
손목이 3° 흔들린 것과 골반이 3° 흔들린 것을 같게 봅니다. 실제로는 다릅니다.

**OKS(Object Keypoint Similarity)** 는 COCO 자세 평가의 표준 지표이고,
여기에 우리가 필요한 게 있습니다.

```
OKS = 평균  exp( −d² / (2·(2σ)²) )
```

`σ`는 **같은 사진을 여러 사람에게 라벨 붙이게 했을 때 서로 어긋난 정도**입니다.
공개된 측정값이고, 관절마다 다릅니다.

| 관절 | σ | |
|---|---|---|
| 손목 | 0.062 | 사람끼리 잘 맞음 |
| 팔꿈치 | 0.072 | |
| 어깨 | 0.079 | |
| 무릎 | 0.087 | |
| 발목 | 0.089 | |
| **골반** | **0.107** | **사람끼리 제일 안 맞음** |

출처: pycocotools `cocoeval.py` — `kpt_oks_sigmas`

**이러면 임계값이 취향이 아니라 측정 한계가 됩니다** — "이 정도 차이는 사람이
봐도 갈립니다"라고 말할 수 있게 됩니다.

### 우리 서비스에 맞게 바꾼 것 4가지

**① 얼굴 관절을 뺐습니다** (코·눈·귀) → 남은 관절 **12개**

⚠️ 처음에 "얼굴 σ가 작아 점수를 지배한다"고 적었는데 **틀렸습니다.**
실측하니 고개를 60° 돌려도 17개 점수는 0.949입니다. 지배하지 않습니다.

실제 이유는 **반대**입니다 — **얼굴이 몸의 신호를 희석합니다.**

| 왼팔 35° 차이 | 점수 |
|---|---|
| 17개 (얼굴 포함) | 0.912 |
| **12개 (몸만)** | **0.876** |

얼굴 5점은 몸이 어떻든 거의 1.0이라 평균을 끌어올립니다. 우리가 잡아야 할 건
몸의 차이인데 그게 묽어집니다. **다만 차이가 크지 않아(0.037) 17개로 해도
크게 안 달라집니다** — 인자로 바꿀 수 있게 뒀습니다.

**② ⚠️ 크기 기준은 몸통 길이입니다. bbox를 쓰면 안 됩니다**

이게 실측으로 찾은 함정입니다. 팔 하나만 20° 움직여도 사각형이 커지고 중심이 밀립니다.

```
s  0.390 → 0.455        중심x  0.500 → 0.464
```

그러면 **가만히 있던 나머지 관절까지 전부 어긋난 것으로 계산됩니다.**

| 왼팔만 20° 움직인 같은 사람 | 점수 |
|---|---|
| bbox 기준 | **0.595** ← 팔 하나 움직였는데 "거의 딴 자세" |
| **몸통 기준** | **0.946** ← 실제로 어긋난 만큼만 |

몸통 길이는 팔다리를 어떻게 벌리든 변하지 않습니다. `F`(프레이밍)가 같은
이유로 이미 몸통 길이를 쓰고 있습니다 — 기준을 맞춘 것입니다.

**③ ⚠️ 회전은 맞추지 않습니다**
Procrustes처럼 돌려서 겹치면 몸이 돌아간 것이 지워집니다. 그건 `R`이 **일부러
잡는** 신호입니다. 위치와 크기만 지웁니다.

> 이게 `F`와 `R`이 별도 관문으로 남아야 하는 이유이기도 합니다.
> **OKS·ML Kit 임베딩·Pr-VIPE 전부 크기나 각도를 정규화로 지웁니다.**
> 우리 downstream(부위별 픽셀 비교)이 그걸 필요로 하는 한, 별도로 재야 합니다.

**④ ⚠️ 화면비를 넘겨야 합니다**
MediaPipe 좌표는 x를 너비로, y를 높이로 **각각** 나눈 값입니다. 거리를 재는
계산은 화면비를 안 맞추면 조용히 틀립니다. 실측 — 같은 자세인데 **0.575 vs 0.463**.
(각도 기반인 `P`·`F`·`R`은 나눗셈에서 상쇄돼 영향 없습니다)

### ⚠️ 과장하면 안 되는 것

**MediaPipe 랜드마크는 COCO 관절과 정의가 완전히 같지 않습니다.**
BlazePose는 어깨·골반을 자체 기준으로 찍습니다. 그래서 이 σ는 **근사입니다.**

- ✅ "COCO의 σ를 가져와 관절별로 다르게 가중했습니다"
- ❌ "COCO와 동일한 OKS입니다"

**그리고 `s`의 눈금도 다릅니다.** COCO σ는 √(세그멘테이션 면적) 기준인데
우리는 몸통 길이 기준입니다. `SCALE_FROM_TORSO = 1.56`으로 임시 보정해뒀습니다.

**→ 그래서 σ를 우리 값으로 재야 합니다.** 그러면 위 두 어긋남이 **동시에**
사라집니다. 우리 검출기, 우리 관절 정의, 우리 크기 기준으로 잰 값이 되니까요.
`SCALE_FROM_TORSO`도 σ 안으로 흡수되어 1이 됩니다.

⚠️ σ는 원래 **데이터셋마다 구하는 상수**입니다(COCO 문서 명시). BlazePose
토폴로지용 공개 σ는 **존재하지 않습니다.** 빌려올 데가 없으니 재는 게 맞습니다.

그리고 우리에겐 그쪽이 **더 맞습니다** — COCO σ는 *사람 라벨러끼리*의 불일치인데,
우리 서비스에 사람 라벨러는 없습니다. 실제 잡음원은 **MediaPipe 흔들림과
사용자의 미세한 움직임**이고, 그게 우리가 재려는 바로 그 값입니다.

### 왜 아직 판정에 안 쓰는가

**잡음을 재기 전에 관문을 갈아끼우면 나아졌는지 판단할 기준이 없습니다.**
지금은 `P`와 나란히 계산해서 화면에 같이 띄웁니다(`web/pose-live.html`).

순서:

| | 할 일 | 필요한 것 |
|---|---|---|
| 1 | **하한 측정** — 가만히 서 있어도 점수가 흔들리는 폭 | 웹캠만 |
| 2 | 상한 측정 — 진단이 뒤집히기 시작하는 자세 차이 | GPU (`scripts/measure_pose_tolerance.py`) |
| 3 | 임계값을 그 사이에 놓고 `P` → `K` 교체 | 1·2 결과 |

**임계값이 하한과 상한 사이에 있으면 "왜 그 숫자냐"에 답할 필요가 없어집니다** —
그 구간 안에서는 결과가 같기 때문입니다. 임의성이 아니라 무관함이 됩니다.

⚠️ **하한 > 상한이면 그건 실패가 아니라 발견입니다** — MediaPipe로는 좋은 자세와
진단을 깨는 자세를 구분할 수 없다는 뜻이고, 지금 알아야 할 일입니다.

## 실시간 촬영은 왜 자동으로 1차를 통과하는가

촬영 화면은 매 프레임 P·F·R을 계산해 화면에 보여주고, **통과 조건을 만족한 순간에
셔터를 누릅니다.** 그러니 그렇게 찍힌 사진은 정의상 통과입니다.

⚠️ **그러려면 프론트와 서버가 같은 임계값을 봐야 합니다.** 프론트에 숫자를
하드코딩하면 서버에서 조정한 순간 어긋납니다 — 화면에서는 통과인데 저장이
거부되는 상황이 생깁니다.

서버가 값을 내려줍니다:

```
GET /api/v1/pose-criteria
{ "tol_deg": 60, "hard_tol_deg": 70, "threshold": 70,
  "f_min": 0.65, "f_hard": 0.4, "min_seg_ratio": 0.25,
  "min_visible_angles": 4, "min_visibility": 0.5, "n_hold": 30 }
```

⚠️ **한 번 흔들리는 걸 방지하려면** `createHoldGate` 를 쓰세요 — 최근
`N_HOLD+3` 프레임 중 `N_HOLD` 개(기본 10)가 통과일 때 셔터를 누릅니다.
손이 지나가다 우연히 맞는 순간에 찍히면 안 되고, 반대로 lite 모델이
한 프레임 튄 것 때문에 0부터 다시 세도 안 됩니다.

## 프론트 구현

⚠️ **문서에 코드를 옮겨 적지 않습니다.** 사본은 반드시 낡습니다.
실제로 쓰는 파일은 하나입니다.

```
web/pose-score.js          의존성 없는 ES 모듈. 그대로 import 해서 쓰세요.
web/pose-score.test.html   브라우저에서 열면 스스로 검사합니다 (설치 불필요)
```

```js
import { evaluate, createHoldGate, fetchCriteria } from "./pose-score.js";

const criteria = await fetchCriteria();      // 앱 시작 시 한 번
const hold = createHoldGate(criteria);

// 매 프레임
const r = evaluate(refLandmarks, userLandmarks, criteria, { multiPerson });
showGuide(r.message);                        // 사용자에게 보여줄 문구
if (hold(r.pass)) shutter();                 // 최근 39프레임 중 30개 통과면 촬영 (약 1초)

// 업로드할 때 이 세 값을 보냅니다
//   r.pose_similarity / r.framing_score / r.facing_delta
```

⚠️ **통과 여부를 프론트가 판단해 보내지 않습니다.** 값만 보내고 판정은 서버가
다시 합니다. `evaluate` 의 `pass` 는 화면 표시용입니다.

⚠️ `reason` 이 `NOT_ENOUGH_JOINTS` 면 **업로드하지 마세요.** 서버는 숫자만 받아
"포즈를 맞춰주세요"라고 답하는데, 실제 문제는 몸이 안 보이는 것이라 사용자가
엉뚱한 걸 고치게 됩니다.
